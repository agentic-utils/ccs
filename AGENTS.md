# CCS - Coding CLI Sessions

## Overview

CLI tool to launch, watch, search and resume coding CLI sessions (Claude Code and Codex) using a bubbletea TUI.

## Development

### Build & Test

```bash
go build
go test -race -v -cover ./...
```

CI runs the whole suite with `-race`, so every test must be race-free and repeatable: a stub read by a goroutine the test started is put back only once that goroutine has ended, and package-level state (caches, throttles, state files) is reset or pointed at `t.TempDir()` per test. `go test -race -count=3 ./...` checks both.

### Test Coverage

- **Target**: 60%+ statement coverage
- **Current**: ~69%
- All new features must include tests
- Break logic into testable functions when possible
- Refactor for testability (e.g., use variables instead of functions for dependency injection)

### Run locally

```bash
./ccs                    # search recent (60 days, <1GB files)
./ccs <query>            # search with initial query
./ccs --max-age=7        # last 7 days only
./ccs --all              # include everything, headless runs too
./ccs -- --plan          # pass flags to claude
./ccs link status        # what opens ccs://session/<name> links (ccs link install sets it up)
./ccs prune --dry-run    # preview lossless size reduction of large files
CCS_CPUPROFILE=cpu.out ./ccs   # record a CPU profile of the whole run (or ^T Q to start/stop one, saved beside the update log); go tool pprof -top cpu.out
./ccs profile --kind cpu --seconds 20   # profile the running ccs TUI from another shell (--role watch|mcp|serve, --pid N, --list)
```

## Release Process

Merging to `main` releases automatically: `.github/workflows/ci.yaml` runs tests, bumps and pushes the tag from the conventional-commit prefixes (`feat:` minor, `fix:`/other patch, breaking-change major), then GoReleaser publishes and updates the Homebrew tap. Never tag by hand; `version` in `main.go` is injected at build time.

Turn on auto-merge as soon as a PR is opened: `gh pr merge <n> --auto --merge` (a merge commit, never squash, never `--admin`). The `main: tests must pass` ruleset requires the `test` check, so GitHub merges it once CI is green, without waiting to be asked; direct pushes to `main` are refused.

Each release's `checksums.txt` is signed by `.github/sign-release.sh` (GoReleaser's `signs`) with `RELEASE_SIGNING_KEY`, a secret of the `release` environment, whose deployment branch policy allows only `main`; ccs refuses to update to a release without a valid `checksums.txt.sig` against the public key in `internal/selfupdate` (`selfupdate.ReleaseKey`). A release job that can't sign fails rather than publishing unsigned. Rotating the key: generate a new one, ship a ccs release with both public keys trusted, then switch the secret; a ccs with only the old key can't update past the switch, so keep the old one until most users have updated.

If a merge's push event is lost and no release runs, start it by hand: `gh workflow run CI --ref main`.

Install the release locally: `brew update && brew upgrade ccs`.

## Architecture

`main.go` at the root holds only `version` (set at build time by `-X main.version`) and `main()`, which calls `tui.Main(version)`, so `go install github.com/agentic-utils/ccs@latest` stays a one-liner. The rest is under `internal/`, one package per area, following the Go team's [module layout](https://go.dev/doc/modules/layout) (no `pkg/`). Each package imports only those listed before it:

- `internal/state` - where ccs keeps its files and logs: `SettingsPath`, `MarksPath`, `UpdateLogPath`, `ActivityLogPath`, `LogUpdate`, `LogActivity`, `AppendLog`, and `Version`, the running release (set by `tui.Main`, read everywhere)
- `internal/proc` - external commands with deadlines (`RunBounded`, `RunCommand`, `RunCommandIn`, `ErrTimedOut`) and process lookups (`MayRun`: a process of that name in the process table, one sysctl with no command lines, true when it can't tell; `PIDAlive`, `ProcessStartTimes` (in-process through kern.proc.pid on macOS, `sysStartTimes`; ps elsewhere), `PsAll`, `PsTree`, `TTYOf`, `SignalPID`, `ShellQuote`, `ShellSafe`), and the socket checks (`socket.go`: `TrustedDir`, `TrustedSocket`, `PeerUID` per OS in `peer_*.go`, `SameUser`, `OwnerOf`; mcp's `trustedSocket`/`peerUID`/`ownerOf` are these); `PsAll` and `PsTree` come from one listing shared for `ListingShare` (1s, under a tick), and a caller waiting on a change calls `Fresh` first; on macOS it's read in-process (`sysListing` in `listing_darwin.go`: kern.proc.all, then kern.procargs2 per process, control characters written `\ooo` as ps does (`psVis`), another user's process or a zombie by its name as ps can't read it either unless setuid; about 15ms where `ps -axww` costs a fifth of a second of CPU), else, or when that fails, `ps -axww`; tests that fake ps turn `sysListing` off; the stubbable ones are vars, which tests swap
- `internal/profiling` - `ccs profile` and the `profile_ccs` MCP tool: profiles of a running ccs with nobody at the keyboard. `Serve(role)` (the TUI, `ccs watch`, `ccs mcp` and `ccs serve` each, from `serveProfiles` in tui/cli.go; the TUI stops it after `p.Run`, which writes a profile it's recording) listens on `SocketPath(pid)`, `<pid>.sock` in `SockDir` (`profile/` beside the settings, 0700, `proc.TrustedDir`; a var, since tests' temp folders are too long for a socket path), 0600; `sweepStale` drops gone pids' sockets. `handle` drops a peer that isn't this user (`proc.SameUser`), reads one JSON line (at most 4KB: `info`, or `start` with only `kind` and `seconds`, checked by `CheckRequest`: cpu, heap or trace, 1 to `MaxSeconds` (300), default `DefaultSeconds`) and answers `started` at once, then `done` once written. `start` takes the machine-wide flock (`machineLock`, `profile.lock` in `SockDir`, non-blocking, so one profile at a time across every ccs) and the in-process mark (`begin`/`end`, `Current`, shared with ^T Q's `StartManual`, so each refuses during the other with `ErrBusy`); a heap profile is written at once after a GC, a CPU profile or trace stops on its own timer or `stopRemote` (Serve's stop). Files are the profiled process's choice (`FileName`: kind, role, pid, time to the millisecond, in `OutDir`, beside the update log, `O_EXCL` 0600) and `Prune` keeps the newest `Keep` (20) of ccs's profiles there, ^T Q's `cpu-<time>.pprof` included. Clients: `dial` (`proc.TrustedSocket`, then `SameUser` on the listener), `Info`, `Targets`, `Pick` (a pid, else the one process of a role, tui by default), `Start` (`Started.Wait` or `Close`, leaving it to stop by itself; the MCP tool, `profileCall` in internal/mcp/profile.go, closes and answers at once with `Describe`, within the tool-call cap), and `Run`, the CLI. `SetOnChange` (the TUI: `profileChangedMsg`, sent with `go p.Send`, since ^T Q starts from Update) redraws the header, which says `recording <kind> profile until <time>` while one runs that ^T Q didn't start. Its `TestMain` points the `state` paths at a temp folder and `SockDir` at a short one in /tmp
- `internal/transcript` - Claude Code and Codex transcripts as `Conversation`s: full and incremental parsing behind `ParseCache` (`ParseLine`, `ParseAppended`, `ParseCodexFile`), `GetConversations`, search text and the search rule (`QueryMatches`, `MatchRank`), background tasks and subagents as recorded, spawned sessions, PR links in gh output (`GHPRCall`, `GHOutputPRs`), messages between sessions (`PeerRef`, `CcsNote`), a message's plain text (`CleanText`: the one cleaner for anything drawn on the terminal, transcript text, topics (`GetTopic` cleans), PR titles and `!` command output alike: escape sequences go whole, 7-bit or C1 (UTF-8 U+009B or a raw 0x9b byte, rewritten to ESC [ by `sevenBitC1` so `ansi.Strip` takes the whole sequence), invalid UTF-8 becomes U+FFFD, C0 but newline and tab, DEL and C1 are dropped; `needsCleaning` is the allocation-free fast path that returns clean text as it was, `HarnessNote`, `ChannelParts`, `PeerParts`, `StripImageNote`), token figures and prices, and `ccs prune` (`RunPrune`, `PruneFile`). Its `TestMain` points the `state` paths and `CodexHome` at a temp folder
- `internal/sessions` - the sessions running on this machine: which are live and their status (`ScanSessions`, `ReadLiveSessions`, Codex's from its processes and rollouts, `LiveCodexSessions`), messages over their sockets (`SendEnvelope`, `ReadSessionFile`, `PeerToken`) with delivery receipts (`ReceiptsCh`, `CloseInboxes`), their terminals (tmux, iTerm, T3 Code, background agents: `FocusSession`, `OpenResumeTab`, `HostOf`, `ListAgents`), putting their tabs in list order for ^T J (`OrderTabs`, in `taborder.go`: `slotOrder` moves only tabs holding a listed session, among the places they hold, so ccs's own tab and shells stay put; tmux by `swap-window -d` with session:index targets (a bare @id can resolve in another session a window is linked into), then re-selecting the window that was current at its new place; iTerm through its API in `itermapi.go`, a hand-rolled websocket on `~/Library/Application Support/iTerm2/private/socket` with a cookie from AppleScript's `request cookie and key` and protobuf ListSessions (106; a tab's sessions from its split tree, minimized sessions and floating panes) and ReorderTabs (125), the windows read last, just before reordering, since it pulls any tab it is given into the window named, and transport errors through `apiErr`, without the socket path, since AppleScript can't move a tab (`move` reports success and does nothing) and Terminal.app can't either, so it's left out; ttys from AppleScript by session unique id; `TmuxRun`, `ITermAPI`, `ITermSessionTTYs`, `ITermCookie` stubbed), `ccs launch` and `ccs close`, `ccs link`, and the open-sessions record. Its `TestMain` stubs every tab, process, Codex and link-handler hook, as `tui`'s does
- `internal/github` - the user's PRs: lookups and status groups (`FetchPRs`, `QueryPRs`, `PRInfo`), the PRs each session touched (`PRsOf`), `ccs watch` (`RunWatch`, `WatchPass`, `PRWatchState`, events in `PREventsPath`), the owner registry (`ccs claim`, `ccs prs`: `RunClaim`, `RunPRs`) and nudges (`NudgeTick`). - `internal/selfupdate` - how ccs updates itself: the latest release (`LatestRelease`, `NewerVersion`), signed checksums (`SignedSums`, `ReleaseKey`), the upgraders (`ChooseUpgrader`, `Upgrader`: Homebrew or the binary in place), downloads (`Download`, `downloadTransport`) and release notes (`ReleaseChangelog`). Its `TestMain` points the logs at a temp folder
- `internal/mcp` - `ccs mcp`, the stdio MCP server (`Main`, `RunMCP`); its tools are described under Architecture below. Its `TestMain` stubs the tab and process hooks `launch_session` and `close_session` reach. `sessions.go` there is `ccs sessions [--json] [--all]` (`RunSessions`, `SessionRows`, `SessionRow`): each running session (`liveSessions`, stubbed in tests) with its status and since when, what it waits for and its question (`Conversation.PendingAsk`, only while `waiting`: a busy session's pending call is one that's running), `asked` (idle and `Conversation.AskedLast`), last API error, PRs (`github.PRsOf`; `open_prs` are those the watcher's state has open, `watchedOpen`, absent with no state), running background tasks and subagents (`transcript.RunningTasks`, `transcript.SubagentRunning`, against the claude process's start) and last message time; waiting first, then asked, then with an error, then newest; `--all` adds sessions not running. ## Conventions

- A focused pane is like a popup: it owns the keyboard and takes single keys of its own. The held-prompt menu takes its keys as soon as its session is selected with the search empty and nothing else has the keyboard (`heldKeysActive`; never behind the usage screen, help, a popup or a chord): ↑/↓, j/k, digits (highlight only), Space, ←, Enter, n (a note, choosing a single-select's highlighted option), Esc (with ❯ on Other… every key but ↑/↓, Enter and Esc types in its field) (back to the list from any step, `menuLeft`, until → or selecting it again; ← goes back a question; Tab is never the menu's: it goes to the next session that needs you) and T as Claude Code's own menu does (a permission prompt: ↑/↓, j/k, Enter or a digit sends its row at once, A yes and D no at once, Esc; no y/n); ^P/^N always move the list and any letter it doesn't use goes to the search; none of them is a global key
- Keys follow Claude Code's prompt: in a text box (the search, the message box) every Ctrl letter edits text as it does there (^A/^E start/end, ^K/^U kill to end/start, ^W kill word, ^Y paste back, Alt+B/F words; `editKey` adds the ^Y the text box lacks). ccs's own actions are chords, Claude Code's own pattern for app actions, under two prefixes (`chordX`, `chordT`, `chording()`; `k = "^x <key>"` or `"^t <letter>"`; the second key may be held with Ctrl, so ^X ^S is ^X S and ^T ^A is ^T A; an unknown chord does nothing, never edits text, and ^T never edits a box). ^X then a key acts on the selected session: ^X B background (the running command, Ctrl+B in the session's tab; see the turn keys below), ^X C closed (the closed sessions under the selected session's fold), ^X D delete, ^X E edit its name, ^X F full details, ^X K kill (stop a background session, or a session in a terminal tab and close the tab; asks y/n), ^X N new session (in its folder), ^X P pin, ^X R restart, ^X S send now (the turn keys below), ^X W wrap up and hand over to the parent, ^X X prune, ^X Z snooze (zzz), ^X Esc interrupt; ^X A another agent (`ccs switch`, `switchLetter` in switch.go: carry the session on in Claude, Codex or Gemini). ^T then a letter is a view, a setting or a tool: ^T A auto-focus, ^T G group, ^T H headless, ^T I install updates automatically, ^T J tabs in list order, ^T L list (hide the sidebar), ^T M move into topics (ccs reorg), ^T O open the orchestrator, ^T Q a CPU profile, ^T T table, ^T U user account, ^T V Remote Control (a popup: t this session now, a every running one, v the setting for sessions ccs starts, w ccs serve, the web page: start or stop its launchd agent, stopping asks y/n), ^T Y your usage (the usage screen, its only key; Esc or ^T Y goes back). Where Claude Code has a chord for the same thing, ccs uses its letter, so a hand that knows Claude Code does the same here: ^X S (Claude Code's ^X ^S, chat:sendNow), ^X B (^X ^B, task:background), ^X K (^X ^K kills its agents; here it stops the session). ^X Enter, Claude Code's queue-submit, is no ccs chord: the message box's Enter already queues a message for a busy session. Single keys that edit nothing stay single: ^R refresh, ^L changelog log, ^O open a link, ^F fork, ? help on an empty search or message box, Tab next session that needs you (`nextWaiting`, by strict priority over `attention`'s tiers: a question ccs holds or a menu or prompt in its tab (`needsYou`), then an idle session whose last message asks something (`waitAsked`), then a done one not read (the cyan ●: live, `liveGroup` 2, `unseen`, not `viewing`; an exited session has no circle so isn't a stop; looking at it and moving on marks it read as usual), then a session with a PR ready to merge (`attentionReady`: `prCounts`' `PRReady`, the PRS column's ✓), then one with any other open PR (`attentionOpenPR`: fix, waiting or draft; not looked up, not found, merged and closed don't count), live or exited; the header's hint is `tabHint` (`needs you`, or `PRs` once only the PR tiers have any), and `anyWaiting` is the first three tiers only; each press goes to the highest tier that has any, re-checked every press, so a new held question is always next; within it, the next after the selection in list order, wrapping (Shift+Tab, `prevWaiting`: the same tier, the one before, wrapping; the held pane passes it on as it does Tab); clears a search hiding it; from the usage screen it goes back first; with none it says "nothing needs you" and does nothing else, never the usage screen), PgUp/PgDn scroll, Alt+↑/↓ move a pinned session. The rule, stated at the top of the ? popup and --help (`keyRule`): single keys act now and leave nothing behind; a chord changes something that stays (a mark, a setting, a file, whether a session runs), ^X for the selected session and ^T for views and tools, and the ones that can't be undone (^X D delete, ^X K stop, ^X R restart, ^X X prune) ask y/n first. The exception is ^X Esc, ^X S and ^X B: they mirror Claude Code's own keys for a running turn, which don't ask, so they act at once (every guard in `turnRefusal` and `turnKeyNow` still applies). A new action is a chord: ^X when it acts on the selected session, ^T when it is a view, a setting or a tool, with a letter that starts its word; when the letter is taken, pick the action's next clear word. Moving a key bumps `keyLayout` and rewrites `keysMovedNote`, so existing installs are told once where it went. Update the header hints, `shortcuts()`, `--help`, the README and the tests together
- Why some actions are single keys and others chords: the text boxes edit like Claude Code's prompt, so ^A ^B ^E ^H ^K ^U ^W ^Y edit text, and ^M ^I ^[ are Enter, Tab and Esc. That leaves only a few Ctrl letters that edit nothing (^C ^L ^O ^R ^S ^V), so most actions have to be chords. ^T is a prefix rather than a key of its own: Claude Code binds it to its todo list, not to editing, and one prefix makes room for every view and setting; ^X alone ran out of letters. The current single keys are what was left over: when the boxes moved to Claude Code's editing keys (d751010), the actions on keys that clashed (^A ^E ^G ^T ^U ^W) became chords and the rest kept their key, and every action added since has been a chord. That history left ^D (delete) a single key while ^X P (pin) was a chord, so delete moved to ^X D, which frees ^D to delete forward in the boxes again. ^F (fork) still takes over the text box's forward-a-character. Don't add a single key just because a Ctrl letter looks free; check it against the editing keys above and the text box's own keymap first
- Every prefix and every popup shows its keys and what they do as soon as it opens, all of them, wrapped to the terminal's width rather than cut: a pending ^X or ^T draws `chordHint` (`chordXPairs`, `chordTPairs`) over the title and search rows, and over the top of the list when it needs more rows; a popup ends with its `hints(...)` row. `TestEveryChordHasAHint` checks every prefix at 80, 120 and 200 columns, that every chord ? help offers is in its prefix's row, and that every popup in `overPopups` draws its keys, so a new prefix, chord or popup can't ship without its hint

- The turn keys are the exception to "a chord's letter starts its word": they use Claude Code's own keys for a running turn, after ^X. ^X Esc interrupts (Esc, at once, no y/n), ^X S sends the queued message now (ctrl+enter's chat:sendNow, pressed as its other binding Ctrl+X Ctrl+S), and ^X B moves the running command to the background (Ctrl+B). Each is offered (`shortcuts()`) and pressed only when it works now (`turnRefusal`): the session is busy, and for ^X S it is writing a reply (no tool call running, `RunningTool`) with a message queued (`QueuedNow`); for ^X B a Bash call is running. Anything else gets a grey note. ^X Esc on anything but a live session is still a cancelled chord

- In the message box, `!` runs a shell command in ccs (in the session's folder), `/` types a slash command into the session, and `!!` / `//` send a line starting `!` or `/` as a message; only a key pressed in the TUI may run or type one. While the box's text starts with a single `!` it is drawn as Claude Code's bash mode (`bashMode`, `asBashMode` in chat.go): the border and a `!` in place of `›` in Claude Code's bashBorder pink (`bashColour`, adaptive: #ff0087 light, #fd5db1 dark), the text's own `!` shown once, and the status line saying where it runs unless a note or the working line holds it

- Every interaction must be possible from the keyboard; the mouse (click, wheel) is only ever a shortcut for something a key already does

- Untrusted text is cleaned where it enters ccs, never left to whoever draws it: `transcript.ParseLine` and `ParseCodexFile` clean what each line adds (`ingest.go`: `cleanSince`), and session files (`SessionFile.cleaned`), subagents' meta.json, `claude agents --json` and GitHub's answers (titles, check names) are cleaned as they're read. Text decoded later (HTML entities, JSON inside a message) is cleaned after decoding (`transcript.DecodeClean`). `TestUntrustedTextIsCleanedWhereItEnters` feeds escapes through every source; a new source or field goes in it
